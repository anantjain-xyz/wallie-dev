# Adopt a reviewed factory improvement

A workspace owner or admin adopts the exact tested configuration from its merged GitHub PR. The Improvements detail links the PR, both benchmark suites, and the resulting activation receipt.

| Proof         | Bound to adoption                                                                                                                                     |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| GitHub        | Numeric repository, PR, frozen base and head commits, merged tree, and latest exact-head approval from an independent human with current write access |
| Configuration | Exact hosted definition bytes recompiled with the current factory catalog and matched to the tested revision and digest                               |
| Qualification | Current targeted and held-out results, exact comparison identities, and the active definition used as their baseline                                  |
| Decision      | Current human Wallie manager, previous and new activation numbers, and both immutable configuration revisions                                         |

- Review the verified draft in GitHub. Mark it ready, obtain an eligible approval, and merge the reviewed head. In Wallie, select **Adopt configuration**, then **Verify GitHub and adopt**.
- Adoption checks the current factory head and qualification in the same transaction that records the receipt and appends the tested revision. A competing activation or withdrawn evidence requires a new decision.
- Resolve an active routing canary through its existing controls before adopting a separate improvement. New admissions use the accepted definition and eligible routing. Existing sessions keep their recorded revision and review state.
- The shared rollback can restore the exact predecessor of the current adoption after a fresh candidate smoke test and current authority checks. Restoring a reviewed routing activation retains its original routing evidence.

## Production outcomes

| Evidence   | How the proposal reports it                                                                                                                                                                                    |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Admissions | Production sessions recorded against the exact activation, revision, and digest on each side of the adoption. Restoring the same digest creates a separate activation.                                         |
| Approval   | Final approval observations and known budget exhaustion of started sessions determine the observed approval rate. Pending work and missing outcome evidence widen the possible rate for all admitted sessions. |
| Delivery   | Counts admitted sessions with at least one current canonical GitHub merge.                                                                                                                                     |
| Spend      | The known subtotal includes finalized measured and estimated attempts. Coverage counts show measured, estimated, pending, and unavailable attempts.                                                            |

- Each cohort needs at least ten resolved sessions and at least 80% resolved coverage. A degradation signal requires the candidate’s upper approval limit to fall below the baseline’s lower limit. These limits describe missing outcomes. The cohorts cover separate admission periods and the comparison is observational.
- On the proposal, an owner or admin can open the exact previous activation in Factory Definition settings. Run a fresh smoke test there and confirm the restore. If the factory head changes, return to the proposal to review the current activation. The proposal retains the adoption, GitHub and benchmark evidence, and the resulting rollback receipt. New sessions use the restored activation and existing sessions keep their admission pins.

See [Factory outcome evidence](factory-outcomes.md) for how lifecycle, verified merge, and usage observations are collected.
